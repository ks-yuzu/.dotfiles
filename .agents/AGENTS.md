デフォルトルールを記載する。リポジトリ側の指定と記載内容が競合する場合はそちらを優先する。

## ドキュメンテーション
- ドキュメントは docs/ 内に配置する
- 実装中に仕様変更・追加があった時は、必要に応じて `docs/spec.md` に追記する

## 作業フロー
- worktree を切る。origin/main が先行していることがあるので注意
- main ブランチに直接 commit せず、PR を作成する
- 作業が完了したら、/code-review でレビューを行う
- 改善まで完了した後、納品を行う
- 受領完了後に、PR のマージ・main ブランチの pull を実施する

## レビュー
- 指摘は鵜呑みにせず裏を取る。記述が不正確なこともあり、追う過程で別の問題が見つかることもある
- 指摘の修正が挙動を変えたなら、もう一度レビューを回す。修正自体が新たな不具合を生む。
  特に入力・イベント・永続化に触る修正は隣を壊しやすい
- 指摘が挙動を変えない類 (ドキュメント、命名、テストの脆さ) だけになったら打ち切り、納品へ進む
- 繰り返す場合はレビューの effort を上げる。安い指摘は前のラウンドで出尽くしている
- 手動確認で不具合が見つかったら、自動テストに盲点がある。直した後にもう一度回す

## テスト
- テストを追加したら、対象を一時的に壊し、落ちることを確認する
- 通ることの確認だけでは「誤った理由で通っている」テストを見抜けない
- 壊しても落ちない場合、その性質は自分のコードではなく依存側が担保している。根拠をコメントに残す

## (主に codex 向け) エージェントの分担
- メインエージェントが設計判断、進捗管理、統合、最終的な品質確認を担当する
- 独立して完結する単純な実装、テスト追加、レビューは Terra / Luna などのサブエージェントへ移譲してよい
- 同じファイルを複数エージェントが同時に編集しない。メインエージェントは差分を確認し、統合後にテストや検証を行う
