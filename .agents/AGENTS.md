全プロジェクト共通のデフォルトルール。リポジトリ側の指示と競合する場合はそちらを優先する。

## 作業フロー

1. worktree を切る。リモートのデフォルトブランチが先行していることがあるので注意
2. デフォルトブランチに直接 commit せず、PR を作成する。spec / ADR はコード変更と同じ PR に含める
3. 作業が完了したらレビューを行い、改善まで済ませる (→ レビュー)
4. 納品する (→ 納品)
5. 受領完了後に、PR のマージとデフォルトブランチの pull を実施する

## ドキュメンテーション

- ドキュメントは docs/ 内に配置する
- 実装中に仕様変更・追加があった時は、必要に応じて `docs/spec.md` に追記する

## 実装

- ファイルを書き換えるスクリプトは冪等にする。置換の前に既適用かを判定する
- 失敗の重さは対称ではない。誤って作用する (誤ったデータを書く) 方が、作用しない (何もしない) より重い。
  曖昧な入力では作用しない側に倒す
- 既存の仕掛けを削る時は、それが何を補っていたかを確かめる。削減が別の機能を壊す

## テスト

- テストを追加したら、対象を一時的に壊して落ちることを確認する。
  通ることの確認だけでは「誤った理由で通っている」テストを見抜けない
  - 落ちないなら、まず層を疑う。**テストはその規則が落ちうる層に置く。コードがある層ではない。**
    移せば落ちるなら移す
  - 層を移しても落ちないなら、その性質は依存側が担保している。根拠をコメントに残す
- 落ちうる層に既にあるテストを、上の層に写さない。写しは弱く、無関係な変化で落ち、ゲートの時間を食う
- テストのために本番へ防御を置かない。本番の入力で到達しない分岐を、到達するよう仕込んだテストが
  支えている形は、テストと規則が互いを正当化する循環である

## 手動確認

- 項目は「引くきっかけ」で分ける。「自分の変更が壊したかも」は触った箇所で引き、
  「相手側が変わったかも」は該当を触った時と報告を受けた時に引く。納品は多くの場合誤ったトリガ
- 手動確認で不具合が見つかったら、自動テストに盲点がある。直した後にレビューをもう一度回す
- 自動テストが育ったら手動確認リストと突き合わせる。放っておくと「既に自動化済み」と
  「誰も見ていない」が混ざる

## 切り分け

- 原因は推測せず計測する。仮説を 1 つ立てたら、それを確かめる観測を用意する
- **主張も計測する。**「下限だ」「全部見た」「これは到達しない」は、1 つずつ確かめてから言う。
  言った時点で相手は検証済みの事実として扱う
- 「効くもの / 効かないもの」の境界を先に確定させる。症状の形が機構を指す

## レビュー

- /codex:review を使う。エージェントから直接呼べないため、codex-companion.mjs を
  バックグラウンドで実行する。利用できない場合は /code-review で代替する
- **「不具合」と「過剰実装」は別々に当てる。**前者は足りないものを、後者は要らないもの
  (到達しない防御、窓を閉じない規則、落ちないテスト、1 呼び出しの抽象、仕様と重複したコメント) を見る。
  不具合レビューからは要らないものは出てこない
- 指摘は鵜呑みにせず裏を取り、対応の要否を検討する。記述が不正確なこともあり、追う過程で
  別の問題が見つかることもある。全てに対応すると過剰実装になるので取捨選択し、
  悩ましい場合 (特にヒューリスティックな判断) は相談する
- 自分の修正にも裏を取る。指摘が名指しした機構を直しても、同じ結末に至る別の経路が残っていれば、
  増えたのは規則だけである
- 修正が挙動を変えたなら、もう一度レビューを回す。修正自体が新たな不具合を生む。
  特に入力・イベント・永続化に触る修正は隣を壊しやすい。繰り返す時は effort を上げる。
  安い指摘は前の巡で出尽くしている
- 止める・相談する条件
  - 指摘が挙動を変えない類 (ドキュメント、命名、テストの脆さ) だけになったら打ち切り、納品へ進む
  - 3 巡目までは承認を取らずに続けてよい。毎巡確認を取ると待ちが入り、その間に他のセッションが
    デフォルトブランチを進める
  - 4 巡目に入る前に止めて相談する。収束していないこと自体が報告すべき事実
  - 同じ箇所が 3 巡連続で回帰したら、規則を足すのをやめる。規則の抜けではなく、判定に必要な
    情報が入力に無い証拠である。機能を削るか、不確実さを利用者に見せる方へ倒す

## 納品

受領依頼の際に以下をまとめて提示する

- PR 一覧
- worktree ディレクトリのパス
- 実行したテストの結果
- 追加したテストの内容・壊し方・結果
- レビューの回数と、指摘の件数・重要度の内訳

## エージェントの分担

- メインエージェントは設計判断、進捗管理、統合、最終的な品質確認に注力する。
  独立して完結する単純な実装やテスト追加は、下位モデルのサブエージェントへ委譲してよい
  (codex: terra / luna、claude: sonnet / haiku)
- 同じファイルを複数エージェントが同時に編集しない。メインが差分を確認し、統合後にテストや検証を行う
